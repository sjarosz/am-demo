# PingAM Lab Getting Started

This guide gets the current lab stack running with:

- PingDS at `ds.jrsz.org`
- PingAM at `am.jrsz.org`
- PingGateway at `ig.jrsz.org`
- three protected apps at:
  - `app1.jrsz.org`
  - `app2.jrsz.org`
  - `app3.jrsz.org`
- one additive OAuth/OIDC demo app at:
  - `app4.jrsz.org`
- Login Widget demo at:
  - `app5.jrsz.org`
- planned future OAuth/OIDC demo hostname:
  - `app6.jrsz.org`

For a full post-clone checklist (vendor distributions, secrets, bootstrap), see [install-after-git-pull.md](install-after-git-pull.md).

The stack uses:

- `docker compose`
- local TLS generated by project scripts
- FQDNs everywhere
- non-interactive AM bootstrap through Amster

## Prerequisites

- Docker Engine or Docker Desktop running
- local `docker compose` available
- these hostnames added to `/etc/hosts`:

## 1. Generate TLS material

Run:

```bash
./scripts/generate-tls.sh
```

This creates:

- the local CA
- service certificates and PKCS#12 keystores
- the shared truststore
- Gateway password files
- `.env` from `.env.example` if `.env` does not exist

Default passwords are `changeit` unless you changed `.env`.

## 2. Start the stack

Bring up the full lab:

```bash
docker compose up -d --build
docker compose --profile bootstrap up --abort-on-container-exit amster-bootstrap
```

What this does:

- builds and starts DS
- builds and starts AM
- runs `install-openam` through the one-shot `amster-bootstrap` container
- creates the local AM realms `/alpha` and `/bravo`
- reapplies the checked-in root OAuth2/OIDC demo config and clones it into `/alpha`
- creates the demo end-user (`DEMO_USER_NAME`) in `/alpha`
- applies Login Widget journey, OAuth client, and CORS for `app5`
- builds and starts the backend apps and Gateway

If you have already completed AM bootstrap once and do not want to re-run the one-shot installer, you can start the long-running services with:

```bash
docker compose up -d
```

This matters on restarts. `amster-bootstrap` is profile-gated and should not run during a normal `docker compose up -d`.

## 3. Validate the lab

Open these URLs in a browser:

- `https://app1.jrsz.org`
- `https://app2.jrsz.org`
- `https://app3.jrsz.org`
- `https://app4.jrsz.org`
- `https://app5.jrsz.org`

At this stage, `app6.jrsz.org` is only a reserved hostname.

Expected behavior:

1. You are redirected to `https://am.jrsz.org:8443/am` in the `/alpha` realm by default
2. After successful AM login, you return to the original app hostname
3. The app page loads through Gateway

You can also use the AM UI directly at:

- `https://am.jrsz.org:8443/am`

## 4. Default credentials

Current lab defaults:

- AM admin username: `amadmin`
- AM admin password: `changeit`
- Demo end-user: `demo-user` / value of `DEMO_USER_PASSWORD` in `.env`

These values come from `.env`.

## 5. Useful commands

Start or rebuild everything:

```bash
docker compose up -d --build
```

Run AM bootstrap again:

```bash
docker compose --profile bootstrap up --abort-on-container-exit amster-bootstrap
```

See running containers:

```bash
docker compose ps
```

Tail logs:

```bash
docker compose logs -f
```

Check only Gateway:

```bash
docker compose logs -f gateway
```

Stop everything:

```bash
docker compose down
```

## 6. What is working today

The current lab supports:

- DS-backed AM install through Amster
- TLS on all major hops
- Gateway host-based routing
- SSO redirect to AM for all three apps
- successful proxying to backend apps after an AM session is presented

## 7. Current lab limitations

These are intentional for now:

- backend TLS in Gateway uses a development-mode hostname-verifier override
- Gateway JWT session encryption keys are temporary across restarts

Those are acceptable for this lab bring-up, but not for a hardened deployment.
